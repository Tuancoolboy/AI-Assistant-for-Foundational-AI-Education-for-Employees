Implementation Notes: Bitemporal Graph Memory

Ngày thực hiện: 2026-06-24

Bởi: Antigravity AI Agent

Spec gốc: Ad-hoc task

1. Quyết định AI tự ra (ngoài spec)

  • Format reasoning_traces: Thay vì append thẳng reasoning_trace vào metadata của bảng learning_paths, chúng tôi lưu nó trực tiếp vào LearningPathState của LangGraph trong quá trình sinh lộ trình. Dữ liệu này được parse từ LLM JSON response (thông qua prompt update).
  • Cấu trúc Frontend Bitemporal Component: Do Vitest đang chạy ở môi trường node không có jsdom/happy-dom được setup, logic tính toán slider time-travel được tách ra hàm calculateBitemporalState thuần tuý trong src/frontend/lib/bitemporal-logic.ts. Hàm này đảm bảo testability cao nhất.
  • API Mock Frontend: Trong quá trình phát triển UI component, do Backend Endpoint (FastAPI) chưa sẵn sàng để phục vụ cho `get_student_trajectory_at`, logic filtering (valid_from vs sliderTime) được tạm thời thực hiện ở Frontend bằng pure javascript array filtering. Điều này đáp ứng chính xác việc Re-render theo thời gian thực khi Admin kéo slider.

2. Những chỗ AI phải thay đổi so với spec gốc

  • Thay đổi LangGraph State: Spec yêu cầu cập nhật state chứa GraphTrajectory. Chúng tôi đã đổi tên biến từ completed_module_ids sang trajectory_edges trong toàn bộ flow (từ data_loader, state, đến nodes và ranking) để đảm bảo đồng bộ ngữ nghĩa.
  • Gộp reasoningTrace vào llm_raw schema: Prompt của LLM được thay đổi từ việc chỉ trả về danh sách lộ trình sang trả về thêm key reasoningTrace. Dữ liệu này được hàm validate_llm_output trích xuất lại.
  • Quyết định thiết kế System Prompt cho Bitemporal Agent: Do giới hạn token budget của System Prompt, chúng tôi chỉ fetch tối đa 5 điểm uốn gần nhất (inflection points) từ temporal_knowledge_edges. Khóa cache (fingerprint) được cập nhật để hash thêm mảng 5 điểm uốn này, đảm bảo lộ trình sẽ bị invalidate và sinh mới khi lịch sử học của học viên có cập nhật (cache miss).

3. Tradeoff AI phải cân nhắc

  • Bảng Append-Only vs Mutating Table cho Bitemporal: Việc chọn Append-Only đáp ứng chuẩn bitemporal (lưu lại superseded_at cho Transaction Time). Tuy nhiên, đổi lại bảng sẽ phình to rất nhanh khi một edge bị sửa đổi nhiều lần (như cập nhật điểm). Giải pháp là dùng index hiệu quả trên `valid_from` và `system_recorded_at`. Cơ chế cleanup log cũ sẽ cần làm ở Phase sau (hoặc offload ra data warehouse).
  • Slider Re-evaluation vs Snapshot: Khi kéo slider, thay vì gửi request đến LLM để re-evaluate lại reasoning tại thời điểm đó (tốn kém và chậm), chúng tôi chọn cách tìm reasoning_trace gần nhất trong quá khứ so với thời điểm slider. Điều này đảm bảo hiệu suất UI 60fps khi kéo slider.

4. Bất kỳ điều gì khác cần lưu ý (Gotchas / Follow-ups)

  • Follow-up 1: Cần triển khai endpoint FastAPI thực tế cho RPC get_student_trajectory_at thay vì fetch và lọc ở Frontend khi số lượng edge lớn.
  • Gotcha: Bảng temporal_knowledge_edges yêu cầu policy RLS rất cẩn thận, đặc biệt liên quan đến quyền của Manager. Hiện tại giả định Manager có thể select data thông qua service_role hoặc RLS tương thích org_id.
